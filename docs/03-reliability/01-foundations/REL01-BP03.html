REL01-BP03: アーキテクチャを通じて固定サービスクォータと制約に対応する

変更不可能なサービスクォータ、サービス制約、物理リソース制限を認識し、これらの制限が信頼性に影響しないようにアプリケーションとサービスのアーキテクチャを設計します。

公式ドキュメント

リスクレベル

このベストプラクティスを確立しないと
中リスク
が発生します！
  • アプリケーションが予想されるすべてのサービス負荷レベルで中断や劣化なしに実行されることを確認

期待される成果

  • 通常および高トラフィック条件下でアプリケーションやサービスが期待通りに動作
  • リソースの固定制約やサービスクォータの制限内で動作するように設計
固定制約を考慮した
アーキテクチャ設計で

固定制約の例

  • ネットワーク帯域幅の物理的制限
  • サーバーレス関数の呼び出しペイロードサイズ
  • API Gatewayのスロットルバーストレート
  • データベースへの同時ユーザー接続数
  • Lambda関数の最大実行時間（15分）
  • SQSのペイロードサイズ（256KB）

一般的なアンチパターン

  • スケール時に設計を失敗させる設計制約があることを知らずに、サービスのリソースを使用する設計を選択する
  • テスト中にサービス固定クォータに到達する非現実的なベンチマークを実行する
  • 固定サービスクォータを超える場合にスケールや変更ができない設計を選択する
  • 高トラフィックイベント中にリスクにさらされる可能性があるサービスクォータのしきい値を監視・アラートする可観測性が設計・実装されていない

実装ガイダンス

  • ソフトサービスクォータや高容量ユニットに置き換え可能なリソースとは異なり、AWSサービスの固定クォータは変更できません
  • ハード制限はService Quotasコンソールに表示されます（ADJUSTABLE = No）
  • ソフトクォータとは異なり、緊急のSeverity 1イベントでもこれらの制限を変更する方法はありません

実装手順

  • アプリケーション設計フェーズで使用される可能性があるAWSサービスの完全なリストをレビューする
  • これらすべてのサービスのソフトクォータ制限とハードクォータ制限をレビューする
  • アプリケーションを設計する際、ビジネス成果、ユースケース、依存システム、可用性目標、災害復旧目標などのワークロードのビジネスおよび技術ドライバーをレビューする
  • リージョンとアカウント間でサービス負荷を分析する
  • ゾーン障害およびリージョン障害時のリソース使用量について回復力アーキテクチャを分析する

テスト戦略：

  • ストレステストでハード制限に到達する可能性を確認
  • 負荷テストで実際の使用パターンを検証
  • カオステストで予期しない障害パターンを発見
