REL06-BP03: 通知を送信する（リアルタイム処理とアラーム）

組織が潜在的な問題を検出した場合、適切な担当者とシステムにリアルタイムの通知とアラートを送信して、これらの問題に迅速かつ効果的に対応します。

公式ドキュメント

リスクレベル

高リスク

このベストプラクティスを確立しないと、問題の早期発見ができず、運用インシデントへの迅速な対応が困難になります。

期待される成果

  • サービスとアプリケーションメトリクスに基づく関連アラームの設定
  • アラーム閾値違反時の適切な担当者とシステムへの通知
  • 運用イベントへの迅速な対応の実現
  • 問題の早期発見と根本原因への対処
適切な閾値設定が重要！
高すぎると重要な通知を逃し、
低すぎるとノイズになります

一般的なアンチパターン

  • 過度に高い閾値の設定により、重要な通知の送信に失敗
  • 低すぎる閾値により、過度な通知のノイズで重要なアラートが無視される
  • 使用量変化時のアラームと閾値の更新を行わない
  • 自動化で対処すべきアラームを担当者に通知し、過度な通知を発生

実装ガイダンス

  • Amazon CloudWatch: メトリクスアラームとコンポジットアラームの作成
  • CloudWatch ダッシュボード: メトリクスとアラートのカスタマイズされたビュー
  • Amazon SNS: アラーム状態変化時の通知配信
  • Amazon EventBridge: CloudWatchイベントに基づくルール実行
  • AWS Systems Manager: OpsItemやインシデントの自動作成
CloudWatchアラームは
静的閾値、異常検出、
その他の基準で設定可能！

アラームアクション

  • SNS通知: Amazon SNSトピックへの通知送信
  • EC2アクション: インスタンスの停止、終了、再起動、復旧
  • Auto Scalingアクション: スケーリングポリシーの実行
  • OpsItem作成: Systems Manager OpsItemの自動作成
  • インシデント作成: Systems Managerインシデントの自動作成

このベストプラクティスを確立する利点

  • 問題の早期発見
  • 運用インシデントへの迅速な対応
  • アプリケーション可用性への影響の最小化
  • 自動化された対応のトリガー
リアルタイム通知により
MTTR（平均復旧時間）を
大幅に短縮できます！
