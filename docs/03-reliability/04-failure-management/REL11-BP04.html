REL11-BP04: 復旧時はコントロールプレーンではなくデータプレーンに依存する

公式ドキュメント

リスクレベル

  • 中リスク
  • コントロールプレーン障害時の復旧遅延
  • RTO・MTTRの増大
  • 複雑な依存関係による復旧失敗
データプレーンは
より安定！

コントロール vs データプレーン

  • コントロールプレーン: CRUDL操作（作成・読取・更新・削除・一覧）
  • データプレーン: 日常的なサービストラフィック処理
  • 例: EC2起動（コントロール）vs リクエスト処理（データ）
  • データプレーンの方が高可用性設計
管理用道路と
本線道路の違い！

静的安定性の実装

  • 事前プロビジョニングで十分な容量確保
  • Auto Scaling回避で新インスタンス起動なし
  • スロットリングでトラフィック制限
  • フェイルオーバーで既存リソース活用
嵐の時は
錨を下ろす！

Route 53の使い分け

  • レコード変更: コントロールプレーン（避ける）
  • DNS応答・ヘルスチェック: データプレーン（推奨）
  • Application Recovery Controller: データプレーン
  • 100% SLAのデータプレーン活用
DNSは道案内
変更は慎重に！

サーバーレスの活用

  • Lambda: 自動スケーリング（データプレーン）
  • DynamoDB: 自動容量調整
  • API Gateway: 自動負荷分散
  • ロードバランサー: 自動ルーティング
サーバーレスは
自動運転！

Kubernetes考慮事項

  • Pod追加: データプレーン（推奨）
  • ノード追加: コントロールプレーン（避ける）
  • オーバープロビジョニングでノード事前確保
  • HPAでPod自動スケーリング
